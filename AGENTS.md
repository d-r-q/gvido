# Инструкции для агентов

Язык прозы по умолчанию — русский. Код, команды, имена файлов и технические идентификаторы сохраняйте в исходном виде.

Это локальное расширение GNOME Shell. Исходники виджета находятся в `runtime.js`, оформление — в `theme.css`, загрузчик — в `extension.js`.

Перед изменениями проверяйте, не отличаются ли исходники от установленной копии расширения. Не перезаписывайте несвязанные правки пользователя.

После изменений проверяйте синтаксис JavaScript командой `node --check` для изменённых файлов и запускайте изолированные проверки `./tests/run-headless.sh`. Подробное описание тестов, ограничений и артефактов: [agents/test-helpers.md](agents/test-helpers.md).

Тестовые файлы не включаются в установленное расширение. Не запускайте проверки на пользовательском `~/todo.md` и не считайте результаты изолированной GNOME Shell подтверждением поведения живой сессии без отдельной проверки.

Пиши коммит-сообщения на русском в совершённом виде: "Кнопка добавления списка сделана менее заметной, чем кнопка добавления задачи".

## UI/UX

### GNOME HIG — источник истины

Для стандартных элементов, состояний и взаимодействий следуй актуальному GNOME Human Interface Guidelines, а не изобретай локальные решения.

В частности, не создавай собственные соглашения для иконок, кнопок, keyboard navigation, focus, hover, цветов и accessibility, если соответствующее правило уже определено GNOME HIG.

### Проектируй систему, а не отдельный элемент

Перед изменением UI определи правило, которому должен подчиняться изменяемый элемент и все его аналоги.

Одинаковые по назначению элементы должны иметь одинаковую визуальную грамматику: геометрию, выравнивание, визуальный вес, spacing и состояния.

Не добавляй one-off styling для исправления одного конкретного элемента, если проблема относится ко всему классу элементов.

### Не смешивай смысл и состояние взаимодействия

Постоянное состояние данных и временные состояния взаимодействия должны визуально различаться.

Например, приоритет задачи, keyboard focus, hover, selection и editing не должны конкурировать за один и тот же визуальный сигнал.

Используй стандартные GNOME-механизмы состояний там, где они существуют.

### UI-задача требует визуальной проверки

Функционально работающий UI не считается завершённым автоматически.

Перед завершением UI-задачи проверь результат целиком:

- визуальную согласованность аналогичных элементов;
- выравнивание, spacing и визуальный вес;
- отсутствие скачков геометрии из-за контента;
- все релевантные состояния;
- управление мышью и клавиатурой.

Если изменённый элемент выглядит правильно изолированно, но нарушает визуальную систему соседних элементов, задача ещё не завершена.
